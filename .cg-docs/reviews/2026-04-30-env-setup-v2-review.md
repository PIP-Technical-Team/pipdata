### P2 — IMPORTANT (should fix)

- **[P2.1]** [cg-testing] `tests/testthat/test-dlw_store_release.R:75-109` —
  `add_log()` → `.pipdataenv` path has no running test coverage. The entire
  block exercising `pd_env_get("log_piperr")` / `pd_env_rm("log_piperr")` is
  wrapped in `if (FALSE)`.
  **Why**: If `add_log()` writes to the wrong key or `pd_env_get("log_piperr")`
  doesn't retrieve it correctly, no test will catch it. The 190-test suite
  passes but none of those tests cover this path.
  **Fix**: Add a focused unit test for `add_log()` in `tests/testthat/test-utils.R`
  (or a new `test-add-log.R`) that verifies the key-naming contract: call
  `add_log("some message", error = "store_release_err", class = "piperr")` then
  assert `!is.null(pd_env_get("log_piperr"))` and `"store_release_err" %in%
  names(pd_env_get("log_piperr"))`. Clean up with `pd_env_rm("log_piperr")`
  in `on.exit()`.

- **[P2.2]** [cg-architecture] `R/utils.R:add_log()` — dynamic
  `paste0("log_", class)` key contract is undocumented. Two `class` values are
  in use in `log_failure()`: `"piperr"` (line 329) and `"unk_err"` (line 337),
  producing `.pipdataenv` keys `"log_piperr"` and `"log_unk_err"`. Callers who
  retrieve these values must independently know to use the same
  `paste0("log_", class)` pattern.
  **Why**: Silent key mismatch risk — a future caller passing a novel `class`
  value and retrieving via `pd_env_get("log_piperr")` gets `NULL` with no
  diagnostic. The dynamic naming is also invisible from the `@param class`
  docs.
  **Fix**: Update the `@param class` roxygen line in `add_log()` to read: `"PIP
  error or warning class. Values are stored in \`.pipdataenv\` under key
  \`paste0("log_", class)\`. Currently used values: \`"piperr"\`,
  \`"unk_err"\`."` Also add an inline comment above the `log_key <-
  paste0("log_", class)` line explaining the convention.
